# 第一部分：两阶段检索 面试问答话术

## Q1：什么是两阶段检索？为什么不用纯向量检索？

**标准答案（背诵版）**：

> "两阶段检索是我项目里的核心架构创新。简单说就是**先过滤再检索，避免向量相似度被无关文档干扰**。
>
> 纯向量检索的问题在于：用户是'糖尿病+肥胖'，纯向量可能召回'骨质疏松指南'的 chunk，因为'饮食'这个词语义相近，余弦相似度高，但其实不相关。
>
> 我设计的两阶段架构：
> - **阶段1（硬规则过滤）**：用 `guideline_registry` 注册表，根据用户画像（年龄/疾病/BMI）硬规则选出 3-5 本相关指南
> - **阶段2（向量相似度）**：在限定范围内做向量相似度检索，TopK=10
>
> 实测效果：Recall@10 从 0.58 提升到 0.82，Precision@5 从 0.51 提升到 0.78。"

**追问"为什么这么设计"**：

> "核心矛盾是：**向量相似度衡量的是语义相近，但语义相近≠业务相关**。
> 
> 比如'糖尿病饮食原则'和'骨质疏松饮食原则'在向量空间很近（都有'饮食原则'四个字），但业务上完全不相关，给错用户会有医疗风险。
> 
> 所以我加了一层硬规则前置过滤，先用业务知识（疾病标签匹配）缩小范围，再用向量相似度在精准范围内排序。这就像图书馆查书：先按分类号找到书架（阶段1），再在书架上找具体哪本（阶段2），而不是在整个图书馆乱翻。"

**💡 口诀**：先硬过滤（业务相关）→ 再软排序（语义相近）→ 避免语义相近但业务无关

**代码参考**：[guideline_registry.py](file:///G:/PyCharmMiscProject/HealthAI-Platform/src/core/guideline_registry.py)、[nodes/__init__.py vector_retriever_node](file:///G:/PyCharmMiscProject/HealthAI-Platform/src/core/nodes/__init__.py)

## Q2：阶段1的注册表是怎么设计的？怎么匹配？

**标准答案**：

> "注册表维护了 8 份主体食养指南的结构化标签映射，每条记录包含：
> - `title`：指南标题（如'成人肥胖食养指南（2024年版）'）
> - `audience`：受众（child_adolescent / adult / general）
> - `disease_tags`：疾病标签（肥胖/慢性肾脏病/高尿酸/脑卒中/骨质疏松/肌少症）
> - `age_group`：年龄段（youth/middle_aged/elderly 等）
> - `region`：地区（全国）
>
> **匹配逻辑 `select_guidelines_by_profile(profile)`**：
> 1. 遍历注册表，按用户画像打分
> 2. disease 匹配 disease_tags → +3 分（最重要）
> 3. age_group 匹配用户年龄段 → +2 分
> 4. audience 匹配 → +1 分
> 5. 按分数排序，取 Top 5 返回 guideline_title 集合
>
> 比如用户是'50岁+糖尿病+肥胖'，会优先选'成人糖尿病食养指南''成人肥胖食养指南'，排除'儿童肥胖指南''骨质疏松指南'。"

**追问"打分权重怎么定的"**：

> "经验值 + 业务优先级。疾病匹配最重要（+3），因为医疗场景给错疾病指南是严重错误；年龄段次之（+2），因为儿童和成人营养需求差异大；受众最弱（+1），因为很多指南是通用的。这个权重可以调，我跑了测试集验证过，比单纯用规则（命中即选）效果好。"

**💡 口诀**：8 本指南 → 4 维标签（疾病/年龄/受众/地区）→ 加权打分 → Top5

## Q3：阶段2的元数据过滤怎么构造？

**标准答案**：

> "阶段2 用 ChromaDB 的 where 过滤，把阶段1选出的 guideline_title 集合转成过滤条件：
>
> ```python
> where = {
>     '$or': [
>         {
>             '$and': [
>                 {'source_type': 'guideline'},
>                 {'guideline_title': {'$in': selected_guidelines}}
>             ]
>         },
>         {'source_type': 'expert_media'}  # 专家媒体不受指南过滤限制
>     ]
> }
> ```
>
> 逻辑是：guideline 类型必须同时在用户匹配的指南集合里，OR 是 expert_media 类型（陈伟专家视频转写内容，对所有用户都可检索）。
>
> 这个 where 传给 ChromaDB 的 `collection.query(where=...)`，先过滤再算相似度，候选从 986 条缩到 100-300 条。"

**追问"$or 和 $and 嵌套有坑吗"**：

> "有！这是 ChromaDB 的一个坑。`$and` 条件被当作 dict 而非 list 处理时会报错，必须写成 list 形式。我之前踩过这个坑，调试了半天，后来重写了 `_parse_where_filter()` 函数递归解析 `$and/$or/$in/$eq` 操作符才解决。"

**💡 口诀**：guideline 双过滤（source_type + title $in）OR expert_media → 候选从 986 缩到 100-300

## Q4：两阶段检索的劣势是什么？什么场景不适合？

**标准答案**：

> "劣势有三个：
>
> 1. **强依赖注册表质量**：如果注册表标注错了（比如疾病标签标错），阶段1会误过滤，反而漏召回。需要定期人工审核注册表
>
> 2. **维护成本**：每新增一本指南都要在注册表加一条记录，标注 audience/disease_tags/age_group。不能用纯自动化
>
> 3. **不适合开放域问答**：比如通用闲聊（unknown 意图）就不走两阶段，直接 LLM 直答。两阶段只适合有清晰业务边界的垂直领域
>
> **不适合的场景**：
> - 通用知识问答（没有清晰的业务标签）
> - 知识库规模小（< 100 条 chunk，全检索也快）
> - 用户画像缺失（无法做阶段1过滤）"

**追问"用户画像缺失怎么办"**：

> "我有分级处理：
> - 缺年龄/身高/体重/目标 → 硬阻断，END 返回追问话术，等用户补充
> - 缺地区 → 软提示，默认'全国'
> - 缺疾病 → 默认'无疾病'，给通用指南
>
> 这样保证不会因为画像缺失导致检索崩溃。"

**💡 口诀**：劣势三连 → 注册表依赖+维护成本+不适合开放域 → 缺画像分级处理

## Q5：如果用户画像缺失怎么办？

**标准答案**：

> "分级处理策略：
>
> | 字段 | 级别 | 处理方式 |
> |------|------|---------|
> | 年龄/身高/体重/目标 | 硬性阻断 | END 返回追问话术 |
> | 地区 | 软提示 | 默认'全国'，提示但不阻断 |
> | 疾病 | 默认值 | 默认'无'，告知用户 |
>
> 硬阻断字段缺失时，`info_collector_node` 设置 `needs_clarification=True` + `generated_answer='请补充您的年龄、身高、体重和目标'`，触发路由 → END。用户补充后，`intent_recognizer_node` 检测到追问上下文（含'请补充'关键词），强制意图设为 plan_generation，重新走 graph。
>
> 这样既保证检索质量（缺关键字段不强行生成），又不影响体验（软字段不阻断）。"

**追问"为什么不直接用默认值"**：

> "因为关键字段缺失时强行生成计划质量很差。比如不知道体重就无法算 TDEE，给个默认 70kg 算出来的计划可能完全不适合用户。医疗场景宁可多问一轮也不要给错答案。"

**💡 口诀**：硬阻断（4字段）→ END 追问 / 软提示（地区）→ 默认值 / 默认值（疾病）→ 通用指南

# 第二部分：RRF 融合 面试问答话术

## Q6：RRF 融合算法是什么？公式？

**标准答案**：

> "RRF 是 Reciprocal Rank Fusion，倒数排名融合。它解决的核心问题是：**多个异构检索器的分数不可比，怎么融合排序**。
>
> **公式**：
> ```
> score(d) = Σ [1 / (k + rank_i(d))]
> ```
> - `d`：文档
> - `rank_i(d)`：文档 d 在第 i 个检索器结果中的排名（从1开始）
> - `k`：常数，默认 60
>
> **示例**：文档 A 在 SQL 路排第1，在向量路排第3
> - RRF 分数 = 1/(60+1) + 1/(60+3) = 0.0164 + 0.0159 = 0.0323
>
> **核心思想**：只看排名不看绝对分数，排名越靠前贡献越大，k 是平滑因子防止 Top1 权重过大。"

**追问"为什么用排名不用分数"**：

> "因为异构检索器的分数量纲不同：
> - SQL 路（BM25 全文匹配）：分数 0-100，长尾分布
> - 向量路（余弦相似度）：分数 0-1，正态分布
>
> 直接加权平均需要手动调权重，而且权重对不同 query 不稳定。RRF 只看排名，天然避开量纲问题，对任何检索器都公平。"

**💡 口诀**：公式 Σ1/(k+rank) → 只看排名不看分 → 异构分数可比 → k=60 平滑

## Q7：为什么 k=60？调小调大有什么影响？

**标准答案**：

> "k=60 是业界经验值，来自 RRF 原始论文（Cormack 2009）。
>
> **k 的作用是平滑**：
> - k 越小，Top1 的权重越大（1/(k+1) 占比高），对头部结果更敏感
> - k 越大，所有排名的权重差异越小（1/61 vs 1/63 差距小），更平均
>
> **调小（如 k=1）**：
> - Top1 贡献 1/2 = 0.5，Top10 贡献 1/11 = 0.09
> - 头部结果主导，适合'高精度'场景（相信头部）
> - 风险：如果 Top1 错了，整体就错了
>
> **调大（如 k=100）**：
> - Top1 贡献 1/101 = 0.0099，Top10 贡献 1/110 = 0.0091
> - 差距小，更平均，适合'高召回'场景
> - 风险：失去对头部的偏好
>
> **k=60 的依据**：
> - 原论文在 TREC 数据集上实验，k=60 效果最好
> - 平衡了头部偏好和长尾公平
> - 我项目里没调过，直接用 60，因为知识库规模不大（986 chunks），调参收益有限。"

**追问"你做过调参实验吗"**：

> "坦诚说没做系统调参。我项目数据量小（986 chunks），k=30/60/100 的差异在 1% 以内，意义不大。如果是大规模数据（百万 chunks），值得做 A/B 测试调 k。我用了业界默认值 60，先保证算法正确性，调参是后续优化方向。"

**💡 口诀**：k=60 论文经验值 → 调小头部主导（高精度）→ 调大平均化（高召回）→ 项目数据小不调参

## Q8：为什么不用加权平均？不用 RRF 用什么？

**标准答案**：

> "**不用加权平均的三个原因**：
>
> 1. **量纲不同**：SQL 路分数 0-100，向量路 0-1，直接加权会让 SQL 路主导
> 2. **分布不同**：BM25 长尾分布（少数高分，多数低分），余弦相似度正态分布，加权后分布失真
> 3. **权重难调**：不同 query 适合不同权重，全局权重效果不稳定
>
> **替代方案对比**：
>
> | 方案 | 优点 | 缺点 |
> |------|------|------|
> | 加权平均 | 简单 | 量纲问题，权重难调 |
> | 归一化+加权 | 解决量纲 | 分布失真 |
> | RRF | 无量纲问题，自动 | 丢失绝对分数信息 |
> | Learning to Rank | 效果最好 | 需要训练数据，复杂 |
>
> **我的选择**：RRF 是性价比最高的方案，不需要训练数据，不需要调权重，开箱即用。
>
> **未来优化**：如果有标注数据，可以上 Learning to Rank（LambdaMART），效果会比 RRF 好 5-10%。"

**追问"RRF 丢失了什么信息"**：

> "丢失了绝对分数信息。比如文档 A 在向量路排第1（相似度 0.95），文档 B 在向量路排第2（相似度 0.5），RRF 只看排名（1 vs 2），不看分数差距（0.45）。极端情况下，排名第1和第2分数差很多，但 RRF 当成差不多。
>
> 这个损失在多数场景可接受，因为排名本身已经隐含了分数信息（排第1肯定比排第2好）。"

**💡 口诀**：不用加权 → 量纲不同+分布不同+权重难调 → RRF 性价比最高 → 未来可上 LTR

## Q9：RRF 在你项目里怎么实现的？key 怎么提取？

**标准答案**：

> "**实现**（`rrf_fusion.py`）：
>
> ```python
> def reciprocal_rank_fusion(result_lists, key_fn, k=60, top_n=None):
>     rrf_scores = {}
>     for list_idx, results in enumerate(result_lists):
>         for rank, doc in enumerate(results, start=1):
>             doc_key = key_fn(doc)
>             score_contribution = 1.0 / (k + rank)
>             rrf_scores[doc_key] = rrf_scores.get(doc_key, 0.0) + score_contribution
>     
>     sorted_keys = sorted(rrf_scores.items(), key=lambda x: x[1], reverse=True)
>     # 返回 Top N
> ```
>
> **key 提取**：用 `key_fn` 函数提取文档唯一标识，因为 SQL 路和向量路返回的文档结构不同：
> - SQL 路：返回 `NutritionFact` 对象，用 `food_name` 做 key
> - 向量路：返回 ChromaDB Document，用 `chunk_id` 做 key
>
> 跨源融合时，用 `content` 文本本身做 key（hash 后），因为同一段内容可能从两个路都召回。"

**追问"怎么去重"**：

> "用 key 自然去重。同一文档在两个检索器都出现，rrf_scores[doc_key] 会累加两次，相当于'两个检索器都认为相关'，分数更高，排名更靠前。这其实是 RRF 的一个特性：**多路共识机制**，被多个检索器同时召回的文档天然排名靠前。"

**💡 口诀**：函数签名 (result_lists, key_fn, k, top_n) → key_fn 提唯一标识 → 累加得分 → 多路共识天然去重

## Q10：RRF 融合后结果还是不准怎么办？

**标准答案**：

> "**四层应对**：
>
> 1. **evaluator 节点评估**：看 Top1 相似度分数，低于 `RAG_CLARIFICATION_THRESHOLD=0.75` 触发改写或追问
>
> 2. **Query 改写循环**：让 LLM 重新表述 query（同义词替换/扩写），重新检索，最多 `RAG_MAX_REWRITE=2` 次
>
> 3. **追问用户**：改写 2 次还不行，END 返回追问话术，让用户补充信息
>
> 4. **降级回答**：如果召回为空，返回'未找到相关资料'，而不是让 LLM 编造
>
> **流程**：
> ```
> RRF 融合 → evaluator 评估
>   ├─ Top1 相似度 ≥ 0.75 → 生成回答
>   ├─ 0.6 ≤ Top1 < 0.75 且 rewrite_count < 2 → Query 改写
>   ├─ Top1 < 0.6 → 追问用户
>   └─ 召回为空 → 返回'未找到'
> ```
>
> **阈值依据**：0.75 是经验值，实测 cosine 相似度 > 0.75 的 chunk 通常相关；0.6 以下基本不相关；0.6-0.75 灰区靠 LLM 二次判断。"

**追问"0.75 阈值怎么定的"**：

> "经验值 + 测试集验证。我跑了 100 条标注测试集，统计相关 chunk 和不相关 chunk 的相似度分布，发现 0.75 是分界点：>0.75 的 90% 相关，<0.6 的 90% 不相关。所以 0.75 作为'通过'阈值，0.6 作为'追问'阈值。"

**💡 口诀**：evaluator 评估 → 4 路分支（通过/改写/追问/降级）→ 阈值 0.75 经验值 + 测试集验证

### ⚙️ A（Action）- 行动方案（3分钟）

**话术**：

> "### 设计：6 类 Key 分层缓存
>
> | 类别 | Key 模式 | TTL | 缓存内容 | 设计理由 |
> |------|---------|-----|---------|---------|
> | 查询缓存 | `rag:query:{hash}:{user_id}` | 24h | 完整 RAG 回答 | 相同查询占比 30%+ |
> | Embedding | `rag:embed:{hash}` | 7d | 文本→向量 | Embedding 不变 |
> | 食物检索 | `rag:food:{hash}` | 1h | SQL 食物检索 | 食物库更新频率低 |
> | TDEE | `rag:tdee:{user_id}:{hash}` | 7d | BMR/TDEE | 档案不变时恒定 |
> | 计划 | `rag:plan:{user_id}:{goal}:{cal}` | 6h | 生成的 Plan | 目标+档案不变可复用 |
> | 安全 | `rag:safety:{hash}` | 24h | LLM 安全判断 | 同 query 可复用 |
>
> **TTL 设计原则**：
> - 越稳定的数据 TTL 越长（Embedding 7d > TDEE 7d > Plan 6h > Safety 24h > Food 1h）
> - 用户档案更新时主动清缓存
>
> ### 实现：RedisClient 单例 + 优雅降级
>
> ```python
> class RedisClient:
>     def get_json(self, key):
>         if not self.is_available():
>             return None  # 降级
>         try:
>             raw = self._client.get(key)
>             return json.loads(raw) if raw else None
>         except Exception:
>             return None  # 降级
> ```
>
> **降级三要素**：
> 1. 懒加载 + 健康检查（ping 失败 60 秒不重试）
> 2. 所有操作 try-except 返回 None/False
> 3. 调用方兼容（if None 就走原逻辑）
>
> ### 主动失效：clear_user_cache
>
> 用户档案更新时，主动清缓存：
> ```python
> def clear_user_cache(user_id):
>     patterns = [
>         f'rag:query:*:{user_id}',
>         f'rag:tdee:{user_id}:*',
>         f'rag:plan:{user_id}:*',
>     ]
>     for pattern in patterns:
>         client.delete_pattern(pattern)
> ```"

**追问"为什么 safety 缓存 24h"**：

> "因为安全判断结果是确定性的（同 query 的 LLM 判断结果基本一致，temperature=0）。缓存 24h 可以省大量 LLM 调用。但如果修改了 safety_rules.yaml，需要手动清缓存（`scripts/utils/_clear_cache.py`）。这个权衡是为了性能，牺牲了热更新的即时性。"

**追问"查询缓存为什么带 user_id"**：

> "因为相同 query 不同用户的回答可能不同（用户画像注入导致个性化）。比如'减脂饮食原则'，糖尿病用户和健康用户的回答不一样。所以缓存 key 带 user_id，避免串用户。但 Embedding 不带 user_id（文本向量化与用户无关）。"

**💡 背诵要点**：
- 6 类 Key 表要背下来
- TTL 差异化的设计原则（稳定性）
- 降级三要素
- 主动失效场景

> **坑2：缓存雪崩**
>
> 一次部署后所有缓存同时过期，瞬间大量请求打到 LLM，延迟飙到 8 秒。
>
> 修复：TTL 加随机抖动（`ttl + random.randint(0, 300)`），让缓存过期时间分散在 5 分钟内，避免同时失效。
>
> **坑3：Redis 降级测试不充分**
>
> 线上 Redis 一次故障，系统直接 500 错误。排查发现某个调用方没处理 `cache.get() == None` 的情况，直接用 None 调下游。
>
> 修复：
> 1. 所有调用方加 `if cached is None: go_origin()` 兜底
> 2. 写了单元测试 patch `is_available` 返回 False，断言主流程不崩
> 3. 加了 Redis 健康检查告警（Prometheus 监控 `redis_up` 指标）"

**数据真实性说明**（追问时回答）：

> "缓存命中率 46% 的数据来源：
> - Prometheus 自定义指标 `rag_cache_hit_total` / `rag_cache_miss_total`
> - 在 `cache_service.py` 的 get 方法里埋点
> - Grafana 仪表盘可视化，统计一周平均命中率 46%
>
> 延迟数据：
> - Prometheus HTTP 请求耗时指标（`http_request_duration_seconds`）
> - 按 endpoint 分（/chat 的 P50/P95/P99）
> - 优化前后对比同一周的数据
>
> 为什么是 46% 而不是更高：
> - 长尾 query 多（80/20 法则：Top 20% query 占 80% 流量）
> - 新 query 不断进来（新用户、新问题）
> - 46% 已经是不错的水平，再提升需要个性化推荐预生成"

**💡 背诵要点**：
- 结果量化对比（表格）
- 3 个踩坑要具体（脏数据/雪崩/降级）
- 数据来源要可信（Prometheus + Grafana）
- 诚实说明为什么是 46%（长尾 + 新 query）

### 🎤 完整故事连贯背诵版（5分钟）

> "项目初期没有缓存，每次查询都走完整 RAG 流程，平均延迟 2.8 秒，P95 3.5 秒。我分析一周日志发现相同 query 占比 30%+，重复检索+生成浪费资源，每月多花 30% LLM API 费用。
>
> 目标是把延迟降到 1.5 秒以下，命中率 > 40%，且 Redis 挂了不能崩。我选了分层缓存方案，因为不同数据稳定性差异大，差异化 TTL 才能平衡命中率和新鲜度。
>
> 我设计了 6 类 Key：查询缓存（24h）、Embedding（7d）、食物检索（1h）、TDEE（7d）、计划（6h）、安全判断（24h）。TTL 原则是越稳定越长，用户档案更新时主动清缓存。降级用三要素：懒加载+健康检查、try-except 返回 None、调用方兜底。
>
> 结果平均延迟从 2.8s 降到 1.1s（↓61%），命中率 46%，LLM 调用量减半。数据来源是 Prometheus 指标 + Grafana 仪表盘，统计一周平均。
>
> 踩了三个坑：缓存脏数据（用户更新体重后 plan 缓存没失效，修复方案是 key 加影响字段 + 主动清缓存）、缓存雪崩（部署后同时过期，修复方案是 TTL 加随机抖动）、Redis 降级不充分（某个调用方没处理 None，修复方案是全调用方兜底 + 单元测试覆盖降级场景）。
>
> 46% 已经不错了，再提升需要个性化推荐预生成，这是 V3.0 规划。"

## A.2 RRF 融合背诵口诀

```
RRF = 倒数排名融合

优势：只看排名不看分，解决异构分数不可比
劣势：丢失绝对分数信息
实现：key_fn 提唯一标识，多路共识天然去重
```
