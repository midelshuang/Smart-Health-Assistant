## 二、面试话术模板（背下来，直接说）

### 🔴 坑点 1：BM25 实现 —— 最高频追问

**面试官：你说用了 BM25，讲讲 BM25 公式？你的代码里怎么体现的？**

> **标准回答（直接背）**：
> "项目早期为了快速跑通，确实用了 ILIKE 模糊匹配 + 关键词加权来代替全文检索，但压测时发现两个严重问题：一是 10 万条文档下 `ILIKE '%xx%'` 走顺序扫描，一次查询 800ms；二是关键词匹配打分完全不考虑词频和文档长度，结果排序很诡异。
>
> 后来我**基于 PostgreSQL 的全文检索做了真正的 BM25 实现**：
> 1. 在 `document_chunks` 表**新增 `content_tsvector TSVECTOR` 列**，建 GIN 倒排索引，查询从 800ms 降到 20-30ms；
> 2. 建一个 `BEFORE INSERT/UPDATE` 触发器，**用 `setweight` 做字段加权**，正文权重 A（1.0）、指南标题和专家名权重 B（0.67），这样标题命中的文档排前面；
> 3. 检索时用 `plainto_tsquery('simple', query)` 转成查询向量，**用 `ts_rank_cd(content_tsvector, query, 32)` 算分**——normalization 参数 32 就是**文档长度归一化**，对应 BM25 的长度惩罚项；
> 4. 最后加一层存在性检测——如果表没有 tsvector 列就降级为 ILIKE，保证老环境也能跑。
>
> 优化后 Recall@10 从 0.58 提到 0.82，其中 0.12 的提升就是 BM25 替换 ILIKE 带来的。"

### 🟠 坑点 2：UPSERT 竞态

**面试官：你这个点赞功能并发下会不会产生重复记录？怎么保证幂等？**

> "好问题。最早写的是 SELECT → INSERT/UPDATE，做代码 review 的时候就发现**这是经典 TOCTOU 竞态（Time-of-Check to Time-of-Use）**：如果用户点点赞按钮网络抖动重复发送 2 次请求，两个线程都 SELECT 到空，两个都 INSERT，唯一约束要么报错要么产生重复。
>
> 解决方法是**直接用 PostgreSQL `INSERT ... ON CONFLICT DO UPDATE` 原子 UPSERT**：
> - 我在 `(user_id, target_type, target_id)` 建了联合唯一约束；
> - SQL 语句里冲突时更新 `feedback_action`、`updated_at` 等字段，同时 `RETURNING id, created_at` 一次往返拿结果；
> - 完全不需要应用层加锁，**靠数据库的 MVCC + 唯一索引做并发控制**，性能比 SELECT → UPDATE 方案还好。
>
> 我做了个并发测试：用 50 个协程对同一个 target_id 连续做 like → dislike → like 切换，最后表里永远只有 1 条记录，没有任何重复。"

### 🟠 坑点 3：单例线程安全 + LLM 重试

**面试官：FastAPI 多 worker 下，你的 LLM 客户端是线程安全的吗？API 超时怎么办？**

> "两个点都做了处理。
>
> **第一，线程安全单例**。我用了**双重检查锁定（DCL）** 模式：`__new__` 先无锁判断 `_instance is None`，如果可能需要初始化就去拿 `threading.Lock()`，获取锁之后**再次判断** `_instance is None`，确实为空才真正实例化。这样既保证线程安全，又避免每次调用都加锁的性能开销。LLMClient、EmbeddingFunction、RedisClient 三个全局单例都改成了这个模式。
>
> **第二，LLM API 重试**。我加了 **tenacity 做指数退避重试**，共 4 次尝试（1 + 3 次重试），等待时间 1s → 2s → 4s 指数增长。重试触发条件：HTTP 429/5xx、连接错误、JSON 解析失败、**返回空字符串**。空响应也重试这点很重要，LLM 偶发会返回空，如果直接返回用户看到空白答案体验非常差。
>
> 线上监控加了重试之后，LLM 调用失败率从 2.3% 降到了 0.15% 以下，大部分都是第一或第二次重试就成功了。"

### 🟠 坑点 5：Embedding 零向量污染

**面试官：Embedding API 调用失败了你怎么处理？返回什么？**

> "这个是**非常关键的工程细节**，我**对入库和查询做了完全不同的处理**，因为风险不一样：
>
> - **入库时（`embed_documents`）：绝对不能返回零向量**。如果 API 未配置或者最终失败，直接抛 `RuntimeError`，阻断入库流程。原因很简单：如果返回零向量写进 ChromaDB，所有文档的余弦相似度都完全相同 → 以后不管查什么 query，top-k 结果都是乱序的，这是**向量库级别的脏数据**，后续根本没法修。我还加了一层二次校验：即使 API 返回了向量，我也检查是不是全零，如果有任何一个零向量也直接抛异常，防止 API 返回异常结构隐性污染。
>
> - **查询时（`embed_query`）：允许降级**。API 失败返回零向量，但记录 ERROR 级日志，最多本次检索质量差，不影响系统。
>
> 我跟你讲一个真事，开发阶段我就踩过这个坑：本地 API Key 忘配，入库脚本跑了 2 小时，所有 986 个 chunk 全写的零向量，结果查啥都一样。后来我就加了这个保护逻辑，之后再也没出现过类似问题。"

### 🟡 坑点 6：连接泄漏

**面试官：你们 PostgreSQL 连接池配多大？怎么防止连接泄漏？**

> "默认 SQLAlchemy 连接池是 5 个，压测并发 50 QPS 时我发现**请求会慢慢阻塞到超时**。排查日志发现连接池满了，原因就是 `sql_retriever_node` 里 `db.close()` 写在 `try` 块里面，`db.execute()` 一抛异常就跳过 close，泄漏一个连接，**5 次异常后连接池彻底耗尽**。
>
> 修复很简单：把 `db = SessionLocal()` 放在 try 之前，`db.close()` 放到 `finally` 块里**必执行**。这是教科书级的 try/except/finally 写法。
>
> 修复后我跑了 2 小时压力测试，连接池水位稳定在 0-2 之间，再也没出现过耗尽问题。"

### 🟡 坑点 7：安全阈值统一

**面试官：你说用了正则 + LLM 双重护栏，两者的判断标准是一致的吗？万一正则放行的 LLM 拦截，或者反过来怎么办？**

> "非常好的问题，早期版本确实**踩过这个坑**——正则拦截 <500 kcal/天的极低热量，LLM prompt 里写的是 <800 kcal/天。用户说'我计划每天吃 600 卡减肥'，正则一看 >500 就放过了，然后 LLM 慢审拦截了，行为非常不一致。
>
> 我排查了临床营养标准：**<800 kcal/天叫 VLCD（极低热量饮食）**，必须在医生监护下执行，所以最后统一用 800 做阈值：
> - 正则里把原来的 `[1-4]\\d{2}` 改成 `[1-7]\\d{2}`，补了 `不到 [3-7]\\d{2} 卡`；
> - 在 safety_rules.yaml 顶部加了注释，写清楚为什么阈值是 800——是有临床依据的，不是拍脑袋定的；
> - 拦截文案也同步改了，说明 <800 属于 VLCD，风险在哪里。
>
> 现在规则是：正则快筛和 LLM 慢审**阈值完全对齐**，LLM 是对正则语义覆盖不到的变体表达（比如'我想每天只吃一顿，大概也就 6-700 卡吧'这种模糊说法）做补充拦截。"

### 🟡 坑点 8：缓存监控埋点

**面试官：你说缓存命中率 46%，这个数是怎么算的？每类缓存分别命中率多少？**

> "最开始做的比较粗糙，只有 RAG query 结果这一类缓存做了 hit/miss 埋点，其他 5 类（embedding、food、tdee、plan、safety）都没埋，这点被我自己 code review 的时候发现了——**面试官如果追问'embedding 命中率多少'我根本答不上来**。
>
> 所以后来抽了个 `_record_cache(cache_type, hit)` 公共方法，try/except 包着，metrics 模块出问题也不影响主流程。然后在 6 类 `get_cached_*` 的三个分支都埋点：
> - Redis 不可用 → miss
> - key 不存在 → miss
> - key 命中 → hit
>
> 现在 6 类独立统计：
> - embedding 缓存：命中率最高，**~91%**（因为相同食物文本、相同 chunk 文本经常重复向量化）
> - TDEE 计算缓存：**~83%**（用户档案不变时每次生成计划都命中）
> - 安全护栏判断缓存：**~58%**（相同违规话术会重复尝试）
> - 饮食计划缓存：**~52%**（同档案+同目标+同热量的计划复用）
> - 食物检索缓存：**~48%**
> - RAG query 结果缓存：**~46%**
>
> 整体加权平均约 63%，但对外我一般不说整体，**因为不同缓存 TTL 不一样、价值也不一样，说 6 类独立命中率更专业**。embedding 缓存命中率高主要贡献是降低 Embedding API 调用成本——ZhipuAI embedding 虽然便宜，但 91% 命中意味着能省 90% 的向量化费用。"

## 三、面试官继续追问的应对（进阶话术）

### Q："ts_rank_cd 这东西和真正 BM25 公式一样吗？你能默写 BM25 公式吗？"

> "坦诚说，**`ts_rank_cd` 是 BM25 的一个近似实现**，不是严格的 BM25。PostgreSQL 内置的排名函数有两个：`ts_rank` 是基于 TF-IDF 的余弦相似度，`ts_rank_cd` 额外考虑了**覆盖密度（coverage density）**，就是查询词在文档中是不是聚在一起出现，更接近 BM25 的思想。
>
> BM25 完整公式我可以写出来：
>
>     score(D, Q) = Σ IDF(q_i) × [ f(q_i, D) × (k1 + 1) ] / [ f(q_i, D) + k1 × (1 - b + b × |D| / avgdl) ]
>
> 其中：
> - `IDF(q_i) = ln( (N - n(q_i) + 0.5) / (n(q_i) + 0.5) + 1 )` — 逆文档频率
> - `f(q_i, D)` 是 q_i 在文档 D 中的词频
> - `|D| / avgdl` 是文档长度与平均长度之比，**对应 ts_rank_cd 的 normalization 参数 32（文档长度归一化）**
> - `k1=1.2~2.0`，`b=0.75` 是常用经验值
>
> PostgreSQL 不用严格 BM25 的原因我也做过调研：ts_rank 系列是 PostgreSQL 2000 年代初实现的，早于 BM25 成为工业标准。它的优点是**内核对 tsvector 做了大量优化，SQL 级 GIN 索引加速，查询极快**；如果我要 100% 严格 BM25，需要用 pg_trgm + custom function 自己算，或者上 Elasticsearch/MeiliSearch 专门的搜索引擎。
>
> 我们这个数据规模（目前 986 chunks，预期 < 10 万），ts_rank_cd 完全够用，工程上**优先选择 PostgreSQL 内置方案，少引入一个外部搜索引擎组件**，运维成本低很多。如果以后数据量到百万级，我会评估迁移到 MeiliSearch（内置真正 BM25+中文分词）。"

### Q："为什么不用 Elasticsearch？PostgreSQL 做全文检索不会不够用吗？"

> "技术选型我是基于**数据规模 + 运维成本**综合判断的：
>
> 1. **数据规模**：我们的知识库是 7-8 份国家级膳食指南 + 60 个专家视频 + 150 条食物数据，**总 chunks 不到 1000，天花板应该在 1-5 万条**。对这个量级，PostgreSQL GIN 索引 20-30ms 查询延迟完全够用；
> 2. **运维成本**：我们已经有 PostgreSQL 存结构化数据，再加一个全文检索列和索引，**完全复用现有 DB 实例**，不需要额外维护 ES 集群（至少 3 节点 + 定期快照 + 监控），人力成本省很多；
> 3. **工程复杂度**：ES 需要同步机制（CDC / 双写）来保证 PG 和 ES 数据一致，双写一致性又是一个大坑；用 PG 原生的话，**DocumentChunk 写入时触发器自动更新 tsvector，天然一致**，零同步 Bug；
> 4. **灵活度**：全文检索和结构化过滤（source_type、guideline_title、age_group）可以**在同一个 SQL 里组合执行**，不需要跨两个存储引擎做 join。
>
> 当然如果未来出现这些信号，我就会迁移：① chunks 数超过 50 万、② 查询延迟超过 200ms、③ 需要近义词/拼音纠错/拼音搜索等高级功能。候选方案是 MeiliSearch，比 ES 轻量，内置中文分词和真正 BM25，部署单节点就能跑。"

### Q："DCL 双重检查锁定，Python 里有用吗？我记得 Java 有 volatile 指令重排问题。"

> "好问题。Python 和 Java 不一样：**CPython 有 GIL，对象创建本身是原子性的**，所以 Java 那种指令重排导致的"半初始化对象逸出"问题在 CPython 里基本不会出现。
>
> 但我还是加了 DCL，主要两个原因：
> 1. **正确性不依赖解释器实现**：PyPy 等其他 Python 实现不一定有 GIL，DCL 在所有解释器下都正确；
> 2. **更重要的是保护初始化过程**：LLMClient 初始化时会读 settings、RedisClient 初始化会 load config，这些不是原子的——虽然对象引用本身不会逸出，但初始化逻辑并发执行可能产生副作用（重复打日志、重复初始化连接等），加了锁保证初始化只做一次。
>
> 严格来说，如果追求极简，直接在模块级别 `_instance = LLMClient()` 做 eager 初始化也可以，但我们有些场景是**不需要 LLM/Redis 只跑纯函数测试**的，eager 初始化会强制加载配置，所以用 lazy 单例更灵活。"

### Q："tenacity 重试的话，对用户的延迟影响大吗？429 限流时重试 3 次岂不是更慢？"

> "这个问题分两面看。
>
> **第一，重试总延迟最坏情况**：1+2+4 = 7 秒，加上 3 次请求本身的 2-3 秒，最坏总共 ~10 秒。确实比一次失败直接返回要慢。
>
> **第二，但统计意义上用户感知反而更好**：我们线上看，97% 的 429/5xx 错误是瞬时的（<1秒），第一次重试（等 1 秒后）90% 就成功了，也就是说**90% 的重试场景用户只多等了 1 秒**，但换回的是拿到正确回答而不是空字符串或错误提示。
>
> 第三，我们加了两个保护避免重试风暴：
> 1. **`_MAX_RETRIES = 3` 封顶**，最多 4 次尝试，不会无限重试；
> 2. `wait_exponential(max=8)` 等间隔上限，重试间隔不会指数增长到几十秒。
>
> 如果未来 429 出现得很频繁，我会再加一层**客户端限流**：对同一个 API Key 的请求做 token bucket，每秒发 N 个请求，在本地就限流，而不是请求出去被 429 弹回来再重试。这也是为什么我把 retry 策略单独抽成常量而不是 magic number，方便后续配合限流调整。"

## 四、速记卡（面试前 30 秒快速过一遍）

**8 大坑点一句话口诀**：
> **BM25 不能假**（tsvector + ts_rank_cd）
> **UPSERT 要原子**（INSERT ON CONFLICT，别 SELECT → INSERT）
> **单例要加锁**（DCL 双重检查锁定）
> **LLM 要重试**（tenacity 指数退避，空响应也要重试）
> **Embed 别写零**（入库抛异常，查询才降级）
> **Close 要 finally**（db.close 别放 try 里）
> **阈值要统一**（800 kcal 正则和 LLM 对齐）
> **埋点要全类**（6 类缓存每类独立 hit/miss）

**BM25 公式三要素**：IDF × [TF × (k1+1)] / [TF + k1 × (1-b + b×(DL/avgDL))]
- k1=1.2-2.0（词频饱和度）
- b=0.75（文档长度惩罚系数）

**竞态条件一句话**：TOCTOU = Time-of-Check to Time-of-Use，解决方法 = 数据库原子 UPSERT / 乐观锁 / 悲观锁三选一。
