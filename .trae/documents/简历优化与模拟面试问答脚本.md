## 1.1 工作经历结构调整

### 当前问题

```

### 优化方案

```
✅ 推荐结构（方案 A）
├── 项目经验 ← 放最前面，绝对主角
│   ├── HealthAI — 企业级健康智能体平台（RAG 方向）

│   ├── 乡村振兴数据管理员  ← 保留但精简，体现综合素质
│   └── 学生项目助理
├── 技术沉淀与开源贡献  ← 可选，精华内容融入项目

| 个人项目→项目经验放最前 | HR 第一眼看到的就是最相关的经历 |

## 2.1 STAR 故事 1：Recall 提升（两阶段检索）

### 面试官完整追问序列

---

#### Q1（开场）：
> "你提到 Recall@10 从 0.58 提升到 0.82，能具体说说你是怎么测的吗？"

**标准回答**：
> "我构建了一份 100 条的标注测试集来评估：
> - 50 条来自真实用户 query（脱敏后），覆盖糖尿病、肥胖、慢性肾脏病等主要疾病场景
> - 50 条是我根据 8 本指南目录设计的覆盖性 query，确保每本指南都有 query 覆盖
> - 每条 query 标注了期望召回的 chunk_id（1-3 个）
> 
> 测试方法：用 query 跑检索，看 Top10 结果里是否包含期望的 chunk_id。
> - 优化前（纯向量）：58 条命中，Recall@10 = 0.58
> - 优化后（两阶段）：82 条命中，Recall@10 = 0.82
> 
> 所有测试代码在 `tests/e2e/test_e2e_rag.py` 里，可以现场跑给你看。"

---

#### 🔥 Q2（刁钻）：
> "100 条测试集有统计学意义吗？会不会是偶然？"

**标准回答**：
> "坦诚说，100 条规模确实不大，不足以做严格的统计显著性检验（通常需要 500+ 才能保证 p<0.05）。
> 
> 但这个测试集是刻意构造的，覆盖了所有核心场景（8 本指南 × 主要 query 类型），所以能反映优化效果的趋势。
> 
> 我也做了交叉验证：用同一测试集跑了 5 次，Recall@10 在 0.80-0.84 之间波动，说明结果稳定，不是偶然。
> 
> 如果是正式上线前评估，我会扩到 500 条 + 引入 RAGAS 自动评估框架，可以算 Precision/Recall/Faithfulness 等完整指标。这是 V3.0 的规划。"

---

#### 🔥 Q3（刁钻）：
> "你说糖尿病召回骨质疏松的问题，能现场演示吗？"

**标准回答**：
> "可以，我帮你复现一下：
> 
> **纯向量检索的问题场景**：
> ```python
> query = "糖尿病饮食原则"
> # 纯向量检索 Top10 可能返回：
> # 1. 骨质疏松指南 chunk（因为"饮食原则"语义相近）
> # 2. 慢性肾脏病 chunk（因为"疾病"+"饮食"）
> # 3. ... 只有 3-4 条是真正相关的糖尿病/肥胖指南
> ```
> 
> **两阶段检索的解决**：
> ```python
> # 阶段1：注册表匹配
> select_guidelines_by_profile({"diseases": ["糖尿病"], "age": 50})
> # → ["中国居民膳食指南（2022）", "成人肥胖食养指南（2024年版）"]
> # （糖尿病没有专属指南，但糖尿病用户常伴随肥胖）
> 
> # 阶段2：where 过滤
> where = {
>     '$or': [
>         {'$and': [{'source_type': 'guideline'}, {'guideline_title': {'$in': selected}}]},
>         {'source_type': 'expert_media'}
>     ]
> }
> # → 候选从 986 条缩到 ~200 条，且都是业务相关的
> ```
> 
> 现场演示：我可以打开 `guideline_registry.py` 给你看注册表结构，然后跑 `test_e2e_rag.py` 里的测试用例。"

---

#### Q4：
> "注册表是手工维护的？每新增一本指南要多久？"

**标准回答**：
> "是手工维护的。8 本指南我花了 2 天标注，因为需要读懂每本指南的适用人群和疾病标签。
> 
> 每新增一本指南：
> - 阅读指南目录和适用人群部分：约 30 分钟
> - 标注 4 个字段（audience/disease_tags/age_group/region）：约 10 分钟
> - 配置 file_patterns（兼容文件名变体）：约 5 分钟
> 
> 总成本约 45 分钟/本。这个成本可以接受，因为国家卫健委的食养指南更新频率很低（一年 1-2 次）。
> 
> 如果未来指南数量多了（>50 本），可以考虑用 LLM 自动抽取元数据做初标，再人工审核。这是 V3.0 的规划。"

---

#### 🔥 Q5（刁钻）：
> "如果注册表标错了（比如疾病标签标错），会发生什么？怎么发现？"

**标准回答**：
> "这是个很实际的问题。如果注册表标错了，阶段1会把用户匹配到错误的指南，导致召回不准确。
> 
> **怎么发现**：
> 1. 定期跑测试集：如果某类 query 的 Recall 突然下降，说明注册表可能有问题
> 2. 分析用户反馈：如果某本指南的引用率异常高或异常低，可能是标注问题
> 3. 定期人工审核：每季度核对一次注册表和 PDF 原文
> 
> **之前踩过的坑**：
> - 注册表里'高尿酸食养指南'的 disease_tags 标成了'高尿酸血症'
> - 但用户画像里是'高尿酸'（口语化表达）
> - 字符串不匹配导致该指南不被选中
> 
> **修复方案**：加了疾病关键词归一化层（`DISEASE_KEYWORD_TO_TAG`），把'高尿酸'='尿酸高'='痛风'='嘌呤'都映射到同一个 tag。这样用户怎么输入都能匹配。"

---

#### Q6：
> "两阶段检索有什么劣势？什么场景不适合？"

**标准回答**：
> "三个劣势：
> 
> 1. **强依赖注册表质量**：如果标注错了，阶段1会误过滤。需要定期人工审核
> 2. **维护成本**：每新增指南要手工标注，不能全自动
> 3. **不适合开放域问答**：通用闲聊（unknown 意图）不走两阶段，直接 LLM 直答
> 
> 不适合的场景：
> - 通用知识问答（没有清晰业务标签）
> - 知识库规模小（<100 条 chunk）
> - 用户画像缺失且无法自动推断
> 
> 我项目里的处理：如果用户画像关键字段缺失，走分级处理——硬阻断字段（年龄/身高/体重/目标）缺失时 END 返回追问话术，软字段（地区/疾病）缺失时用默认值。"

---

#### 🔥 Q7（刁钻）：
> "让你重新设计两阶段检索，你会做什么改进？"

**标准回答**：
> "三个改进方向：
> 
> **改进1：注册表自动构建**
> - 用 LLM 读取指南 PDF 的目录和适用人群章节
> - 自动抽取 audience/disease_tags/age_group 等字段
> - 人工审核确认，节省标注时间
> 
> **改进2：召回后加 reranker**
> - 两阶段检索后，用 bge-reranker-base 做精排
> - 这个 cross-encoder 模型比 RRF 更准，预估 Recall 再提升 5-10%
> 
> **改进3：引入 Learning to Rank**
> - 收集用户点击/反馈数据做训练集
> - 用 LambdaMART 替代 RRF 融合
> - 对不同 query 类型自动学习最优权重
> 
> 但这些改进都是在当前架构验证有效后的渐进式优化，不会大改架构。"

## 2.2 STAR 故事 2：缓存命中率（Redis 分层缓存）

### 面试官完整追问序列

---

#### Q1（开场）：
> "你提到缓存命中率 46%，这个数据是怎么统计的？"

**标准回答**：
> "通过 Prometheus 自定义指标采集的：
> 
> 1. **埋点位置**：在 `cache_service.py` 的 `get_cached_query` 等所有 get 方法里
>    - 命中时调用 `record_cache_hit(cache_type=xxx, hit=True)`
>    - 未命中时调用 `record_cache_hit(cache_type=xxx, hit=False)`
> 
> 2. **指标定义**：`src/utils/metrics.py` 里定义了
>    ```python
>    rag_cache_hit_total = Counter('rag_cache_hit_total', ['cache_type', 'hit'])
>    ```
> 
> 3. **统计方法**：
>    - Grafana 仪表盘实时展示各类型缓存的命中率
>    - 统计一周数据（排除部署/故障等异常时间段）
>    - 总命中率 = hit / (hit + miss) = 46%
> 
> 可以现场打开 Grafana 仪表盘看实时数据。"

---

#### 🔥 Q2（刁钻）：
> "46% 命中率算高还是低？为什么没到 80%？"

**标准回答**：
> "46% 是合理的水平，原因有三个：
> 
> **原因1：长尾 query 多**（80/20 法则）
> - Top 20% query 占 80% 流量（'苹果热量''减脂饮食原则'这类高频 query）
> - 这些高频 query 的缓存命中率接近 100%
> - 但剩下 80% 是长尾 query（'我最近尿酸有点高该怎么吃'），几乎不会重复
> 
> **原因2：新用户多**
> - 新用户的个性化 query（带 user_id 的缓存）不会命中旧用户的缓存
> - 查询缓存带 user_id 是为了避免串答，但牺牲了命中率
> 
> **原因3：缓存 TTL 限制**
> - 查询缓存 TTL 24h，用户隔了两天再问同样的问题就不会命中
> 
> 如果想提升到 80%，需要：
> - 对高频 query 做预生成（提前缓存热门 query 的回答）
> - 用 ML 预测用户可能会问的 query，提前生成缓存
> 
> 但 46% 的投入产出比已经很高了，再提升的边际成本递增。"

---

#### 🔥 Q3（刁钻）：
> "缓存脏数据是怎么回事？能具体说说吗？"

**标准回答**：
> "这是我上线后遇到的一个真实问题：
> 
> **现象**：用户反馈'我昨天更新了体重，今天生成的计划还是按旧体重算的'
> 
> **排查过程**：
> 1. 查 Redis key：`rag:plan:user_123:fat_loss:1800`
> 2. 发现 key 里只有 user_id + goal + calories，没有体重
> 3. 用户从 70kg 减到 65kg，TDEE 从 2100 kcal 降到 1950 kcal
> 4. 但缓存 key 里的 calories 是 1800（旧 TDEE 计算的目标），新的 TDEE 是 1650
> 5. 缓存没失效，命中了旧数据
> 
> **根因**：缓存 key 设计时没有包含所有影响结果的字段
> 
> **修复方案**：
> 1. **改进 key 设计**：在 key 里加用户档案 hash
>    ```python
>    # 修复前
>    key = f"rag:plan:{user_id}:{goal}:{target_cal}"
>    # 修复后
>    key = f"rag:plan:{user_id}:{goal}:{profile_hash}:{target_cal}"
>    ```
> 2. **主动失效**：用户档案更新时调 `clear_user_cache(user_id)` 清所有相关缓存
> 3. **加监控**：如果用户体重/身高变了 >5%，主动清缓存
> 
> 这个坑让我意识到：**缓存 key 设计要包含所有影响结果的输入参数**，不能偷懒用 user_id 做 key。"

---

#### Q4：
> "Redis 挂了系统会怎么样？你怎么保证不崩？"

**标准回答**：
> "我做了**优雅降级三要素**：
> 
> **要素1：懒加载 + 健康检查**
> ```python
> def is_available(self):
>     if self._available is True:
>         return True
>     if self._available is False:
>         # 失败后 60 秒内不重试
>         if time.time() - self._last_check_ts < 60:
>             return False
>     # 真实连接检查
>     client = self._get_client()
>     client.ping()
>     self._available = True
>     return True
> ```
> 
> **要素2：所有操作 try-except 返回 None/False**
> ```python
> def get_json(self, key):
>     if not self.is_available():
>         return None  # 降级
>     try:
>         raw = self._client.get(key)
>         return json.loads(raw) if raw else None
>     except Exception as e:
>         return None  # 降级
> ```
> 
> **要素3：调用方兼容**
> ```python
> cached = get_cached_query(query, user_id)
> if cached is None:
>     result = do_expensive_call()  # 走原逻辑
> else:
>     result = cached  # 命中缓存
> ```
> 
> **真实验证**：我写了单元测试 `test_redis_degradation`，patch `is_available` 返回 False，断言主流程不崩，所有操作返回 None/False。上线后 Redis 确实挂过一次（运维操作失误），系统自动降级，用户无感知。"

---

#### 🔥 Q5（刁钻）：
> "缓存雪崩怎么解决的？"

**标准回答**：
> "**什么是缓存雪崩**：大量 key 同时过期，瞬间所有请求打到后端（LLM/DB），导致后端过载。
> 
> **我项目里的场景**：部署后如果所有缓存同时过期，Redis 瞬间空了，大量 query 打到 LLM，延迟飙到 8 秒。
> 
> **解决方案**：TTL 加随机抖动
> ```python
> import random
> 
> def set_cached_query(query, result, user_id):
>     # 基础 TTL 24h + 随机抖动 0-5 分钟
>     jitter = random.randint(0, 300)
>     ttl = KEY_TTL_QUERY + jitter
>     client.set_json(key, result, ttl)
> ```
> 
> 这样缓存过期时间分散在 5 分钟内，不会同时失效。
> 
> **多级缓存兜底**：
> - 本地内存缓存（LRU，容量 1000）缓存热点 query
> - Redis 做二级缓存
> - 如果 Redis 挂了，直接走原逻辑（LLM 调用）
> 
> **监控告警**：Prometheus 监控 `redis_up` 指标 + 缓存命中率，命中率突降 30% 触发告警。"

---

#### 🔥 Q6（刁钻）：
> "如果让你重做缓存策略，你会改什么？"

**标准回答**：
> "三个改进方向：
> 
> **改进1：多级缓存架构**
> - L1：本地内存缓存（LRU，热点 query）
> - L2：Redis（6 类 Key 分层）
> - L3：CDN（静态资源 + 热点 API 响应）
> 
> **改进2：缓存预热**
> - 定时任务每天凌晨预生成前一天 Top 100 高频 query 的缓存
> - 用户活跃时段（早 8-9 点、午 12 点、晚 7-8 点）前 10 分钟预热
> 
> **改进3：缓存主动失效机制**
> - 数据更新时（如营养成分表更新）主动清相关缓存
> - 用消息队列（Redis Pub/Sub）通知所有节点清缓存
> - 支持标签化失效（清所有带 'nutrition' 标签的缓存）
> 
> 另外可以引入 **Cache Aside + Write Behind** 混合模式：
> - 查询用 Cache Aside（先查缓存，miss 再查 DB，然后回填缓存）
> - 写入用 Write Behind（先写缓存，异步写 DB，适合高吞吐场景）"

### 🎯 根因分析

```
根因链：
Redis 故障
  → 所有请求降级到 LLM
  → LLM API 过载（正常 QPS 50 → 突增 200）
  → LLM 响应变慢（200ms → 5s）
  → LLM client 超时设置 30s 太长
  → 部分请求等待 30s 才超时
  → 超时后抛异常
  → 部分异常没被捕获
  → 500 错误
```

**根本原因**：降级策略只考虑了"单请求降级"，没考虑"降级后的并发压力"。
